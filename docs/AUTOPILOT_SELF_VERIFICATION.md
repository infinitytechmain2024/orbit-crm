# Автопилот: планировщик и верификатор

Как устроен полный жизненный цикл инженерной задачи в `coding_executor` — от
декомпозиции до браузерного самотеста — и что нужно настроить, чтобы он работал.

## Зачем

Раньше автопилот был одношаговым: одна задача → один цикл tool-calling → PR.
Проверить, что он действительно сделал то, что заявил, можно было только руками.
Теперь run состоит из пяти фаз, и каждая оставляет проверяемый артефакт.

## Пять фаз

| Фаза | Модуль | Артефакт |
| --- | --- | --- |
| 1. План | `backend/services/autopilot_plan.py` | `docs/autopilot/plans/<task>.md` в том же PR |
| 2. Исполнение с трекингом | `backend/services/coding_executor.py` | статус каждого шага в файле плана |
| 3. Ревизия кода | `backend/services/autopilot_verifier.py` | список findings в отчёте и в ленте задачи |
| 4. Браузерный самотест | `e2e/autopilot-smoke.spec.ts` | статус `passed`/`failed`/`skipped` + вывод теста |
| 5. Отчёт | `autopilot_verifier.render_report` | тело PR и `ai_tasks.result` |

### 1. План

До первой правки модель получает задачу и возвращает от 2 до 12 атомарных
шагов. Они рендерятся в Markdown-файл по фиксированному пути
`docs/autopilot/plans/<task-id>-<slug>.md` и попадают в тот же pull request,
что и код. Если планировщик недоступен или ответил мусором — берётся
детерминированный план из критериев приёмки: run не должен падать из-за
планирования.

### 2. Исполнение с трекингом

К обычным инструментам (`read_file`/`edit_file`/`write_file`/`search`/
`list_dir`/`run_command`) добавлен `check_changes` и три инструмента плана:

- `complete_step(step_id, note)` — шаг сделан;
- `block_step(step_id, reason)` — шаг сделать нельзя, **run продолжается** по
  остальным шагам;
- `show_plan()` — текущие статусы.

Каждый вызов немедленно переписывает файл плана. Это важно: run, убитый по
таймауту, всё равно оставляет честную картину того, докуда он дошёл.

Вызвать `finish` с шагами без статуса нельзя — исполнителю один раз вернётся
список незакрытых шагов с требованием закрыть каждый через `complete_step` или
`block_step`.

### `check_changes` — дельта вместо фона

В репозитории есть накопленные чужие ошибки (на момент написания — 142
диагностики `tsc` и 3 падающих теста). Если показать модели этот вал, вопрос
«я что-то сломал?» становится неотвечаемым, поэтому `check_changes` берёт список
изменённых в этом ране файлов из `git diff --name-only` и фильтрует вывод по ним:

```
Проверка «typescript»: 1 замечани(й) в изменённых тобой файлах
(всего в проекте — 142, остальное существовало до тебя).
src/lib/probe.ts(3,10): error TS18048: 'value' is possibly 'undefined'.
```

Доступны `typescript` (`tsc --noEmit`), `lint` (`eslint`) и `tests` (`pytest`).
Первые две требуют `node_modules`: в свежем клоне их нет до фазы верификации, и
инструмент прямо об этом сообщает, а не падает с «command not found».

### 3. Ревизия кода

Ревьюер получает **реальный `git diff`**, а не рассказ модели о том, что она
сделала. Это ловит главный класс отказов: отчёт об успехе для правки, которая
не применилась или ушла не в тот файл.

Findings уровня `blocker`/`major` возвращаются исполнителю на один
ограниченный круг починки (`REPAIR_STEPS`), после чего дифф пересматривается
заново. То, что осталось, уходит в тело PR и в событие
`autopilot_review_findings` — не теряется, а при `AUTOPILOT_BLOCKER_POLICY=draft`
ещё и открывает PR черновиком, чтобы его нельзя было смёржить случайно.

Большой дифф не обрезается молча: он режется по файлам на несколько запросов
ревью, findings дедуплицируются, а файлы, не поместившиеся в бюджет,
перечисляются в отчёте отдельным замечанием.

Выключается через `AUTOPILOT_SELF_REVIEW_ENABLED=false`.

### 4. Браузерный самотест

Playwright поднимает приложение, логинится **локальным тестовым аккаунтом**,
проходит по маршрутам и падает на фатальных ошибках в консоли.

Статус `skipped` — полноценный результат: ненастроенное окружение не должно
выглядеть как пройденный тест.

Провал самотеста **не отменяет PR**: он помечает верификацию как `failed`,
кладёт вывод теста в отчёт и передаёт дефекты в QA-фазу воркфлоу.

Сценарий выбирается под задачу: `select_spec` сопоставляет заголовок, описание,
критерии приёмки и изменённые файлы с именами спек в `e2e/`. Смоук — нижняя
граница, а не потолок. Что именно прогонялось, видно в `verification.spec` и в
отчёте.

### 5. Отчёт

`CodingExecutionResult` несёт `plan`, `review_findings`, `verification` и
готовый `report`. `orbit_commander` кладёт их в `ai_tasks.result` и публикует
события `autopilot_plan_completed`, `autopilot_review_findings`,
`autopilot_verification`.

## Настройка браузерного самотеста

```bash
cp .env.e2e.example .env.e2e.local
```

Тестовый аккаунт заводится руками — агент не создаёт учётные записи и не вводит
пароли.

Заполните `.env.e2e.local` (он git-ignored и должен таким остаться):

| Переменная | Назначение |
| --- | --- |
| `AUTOPILOT_E2E_ENABLED` | включает фазу 4; по умолчанию `false` |
| `AUTOPILOT_E2E_EMAIL` / `AUTOPILOT_E2E_PASSWORD` | **выделенный** тестовый аккаунт, не рабочий |
| `AUTOPILOT_E2E_BASE_URL` | где Playwright ждёт приложение (по умолчанию `http://localhost:8080`) |
| `AUTOPILOT_E2E_SUPABASE_ANON_KEY` | публичный anon-ключ для фронтенда под тестом |
| `AUTOPILOT_SELF_REVIEW_ENABLED` | фаза 3; по умолчанию `true` |
| `AUTOPILOT_CACHE_DIR` | общий кэш npm и браузеров Playwright; по умолчанию `.selfdev/cache` |
| `AUTOPILOT_WORKSPACE_SLOTS` | сколько worktree переиспользуется параллельно; по умолчанию 2 |
| `AUTOPILOT_BLOCKER_POLICY` | `draft` (по умолчанию) открывает PR черновиком при оставшемся блокере; `warn` — прежнее поведение |

### Кэш между ранами

Каждый ран работает в одноразовом клоне, поэтому без кэша, который его
переживает, каждый раз заново качается всё дерево зависимостей и браузер — самая
дорогая часть фазы 4. `AUTOPILOT_CACHE_DIR` задаёт постоянный каталог, на
который указывают `npm_config_cache` и `PLAYWRIGHT_BROWSERS_PATH` (он под
`.selfdev/`, то есть уже git-ignored). Значение, явно экспортированное с хоста,
имеет приоритет. Установка идёт через `npm ci`, если есть `package-lock.json`,
с откатом на `npm install`. Недоступный каталог кэша означает медленный ран, а
не упавший.

Локальный прогон вручную:

```bash
E2E_EMAIL=... E2E_PASSWORD=... npx playwright test e2e/autopilot-smoke.spec.ts
```

Без переменных сценарий пропускается — это ожидаемое поведение, а не поломка.

## Рабочая копия

Ран не клонирует репозиторий заново. На каждый репозиторий заводится один
голый репозиторий (`AUTOPILOT_CACHE_DIR/repos/<slug>/mirror.git`), а раны берут
слот из пула долгоживущих worktree. Между ранами слот жёстко сбрасывается и
чистится — кроме `node_modules`, сохранение которого и делает браузерный тест
доступным по времени. Слоты защищены файловой блокировкой, так что два воркера
никогда не делят один чекаут; занятый пул, недоступный кэш или недостижимый
remote означают откат на одноразовый клон, а не отказ рана.

Голый репозиторий намеренно **не** `--mirror`: зеркало отображает
`refs/*:refs/*`, и `fetch --prune` удалил бы ветку автопилота, которая есть
локально, но не запушена — то есть ровно тот коммит, ради которого существует
возобновление доставки. С рефспеком `+refs/heads/*:refs/remotes/origin/*`
prune трогает только remote-tracking-ссылки.

Поскольку ссылки переживают ран, `_resume_delivery` находит недоставленный
коммит предыдущей попытки и просто дожимает push и PR, не выполняя работу
заново. По той же причине имена веток теперь проверяются на коллизии — при
одноразовом клоне они были уникальны по построению.

## Бюджеты времени

Фазы обязаны укладываться в таймаут job'а, иначе воркер убьёт ран на середине —
именно поэтому фаза 4 не могла завершиться при дефолтных 900 с.

| Что | Константа | Значение |
| --- | --- | --- |
| Клон | `CLONE_TIMEOUT_SECONDS` | 420 с |
| План + исполнение + ревизия + починка | `EXECUTION_BUDGET_SECONDS` | 1200 с |
| Установка зависимостей + браузер + прогон | `VERIFICATION_BUDGET_SECONDS` | 1500 с |
| Запас на commit/push/PR | `JOB_TIMEOUT_MARGIN_SECONDS` | 240 с |
| **Итого** | `total_run_budget_seconds()` | **~56 мин** |

`orbit_commander.enqueue_job` берёт таймаут execute-job'а из
`total_run_budget_seconds()`, но только для ролей, которые действительно идут в
coding executor. Остальные фазы и роли сохраняют прежние 900 с, чтобы зависший
job не выявлялся час.

Внутри рана два дедлайна: циклы исполнения ограничены `EXECUTION_BUDGET_SECONDS`
и не могут съесть долю верификации, а верификатор получает остаток и режет по
нему таймаут каждого шага. Не хватило времени — `skipped` с причиной, а не
обрыв. Фактические длительности возвращаются в `CodingExecutionResult.timings`.

## Что происходит, если изменения не удалось доставить

Сбой `git push` или создания PR — это отказ доставки, а не отказ работы. Он
возвращается как `success=False` с сохранёнными планом, findings и результатом
верификации, а не выбрасывается наверх: иначе воркер ретраит job целиком, заново
клонируя репозиторий и заново прогоняя модель. Создание PR идемпотентно (уже
открытый PR для ветки переиспользуется), а имя ветки содержит номер попытки,
поэтому повторный ран не конфликтует с частично доставленным предыдущим.

## Что видно в интерфейсе

Карточка задачи показывает `AutopilotRunPanel`: статус каждого шага плана,
результат браузерного самотеста с именем прогнанного сценария, findings
самопроверки и ссылку на PR. Разбор `ai_tasks.result` живёт в
`src/features/ai-workflow/autopilot-result.ts` и покрыт тестами на битые данные —
колонка нетипизированная, а строки, созданные до автопилота, этих полей не
содержат.

## Метрики

`autopilot_metrics.run_metrics` разворачивает результат рана в строку метрик,
`aggregate` сводит набор ранов. Строка публикуется событием `autopilot_metrics`
в ленте задачи. Две тонкости намеренны: ран без плана даёт `None`, а не нулевую
полноту, иначе «плана не было» усреднится с «ничего не сделано»; `skipped`-
верификация не попадает в знаменатель pass rate, иначе ненастроенное окружение
выглядело бы зелёным.

## Инварианты безопасности

Они держатся кодом, а не формулировкой промпта:

- **Только ветки `autopilot/*`.** `_branch_name` жёстко добавляет префикс, а
  `_create_branch_and_commit` и `_push_branch` содержат assert против
  `main`/`master`. Пуша в дефолтную ветку нет нигде в модуле.
- **Секреты не попадают в argv.** Токен GitHub уходит в git через
  credential-helper и переменную окружения; пароль тестового аккаунта — через
  окружение Playwright. Именно argv утекает в сообщения об ошибках, в список
  процессов и в логи задач.
- **У браузерного теста нет лишних секретов.** Окружение сабпроцесса собирается
  с нуля, а не копированием `os.environ`, поэтому `GITHUB_TOKEN`,
  service-role-ключ Supabase и ключи AI-провайдеров структурно отсутствуют в
  процессе теста.
- **Вывод скрабится в два прохода.** Любой захваченный stdout проходит через
  `autopilot_verifier.scrub` до попадания в отчёт, PR или лог: сначала по
  известным значениям из настроек, затем по образцам (JWT, `ghp_`,
  `github_pat_`, `sk-`, `nvapi-`, `xox*`). Одного прохода мало: по значениям не
  вычистить секрет, которого этот процесс никогда не держал — например, JWT,
  напечатанный браузерным тестом из сетевого лога.
- **Файлы `.env*` и `.git/` недоступны на запись** ни одному инструменту модели.

Тесты на эти инварианты: `backend/tests/test_coding_executor.py`,
`backend/tests/test_autopilot_verifier.py`.

## Точки расширения

- Список шагов ограничен `autopilot_plan.MAX_STEPS` (12) — задачу крупнее
  следует резать на несколько `ai_tasks`, а не растягивать план.
- Бюджеты времени: `RUN_TIMEOUT_SECONDS` покрывает весь жизненный цикл,
  `REPAIR_STEPS` — размер круга починки.
- Сценарий самотеста задаётся аргументом `spec` у
  `run_browser_self_test(workdir, spec=...)`, если для конкретной задачи нужен
  свой user flow.
