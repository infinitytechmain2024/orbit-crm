Продолжение [self-verification-loop.md](self-verification-loop.md). Каждый пункт

## P0. Без этого пятифазный цикл не доживает до конца

### [x] 1. Свести бюджеты времени — сейчас они не сходятся

**Проблема.** Воркер убивает job по таймауту задачи:
`asyncio.wait_for(..., timeout=max(30, task.timeout_seconds or 900))`
([workflow_worker.py:82](../../backend/services/workflow_worker.py#L82),
дефолт задаётся в [orbit_commander.py:885](../../backend/services/orbit_commander.py#L885)) —
это **15 минут**. Внутри одного рана:

| Этап | Бюджет |
| --- | --- |
| `git clone --depth 1` | до 420 с (реально ~2 мин, ~465 МБ) |
| планирование + цикл исполнения + починка | до 1800 с (`RUN_TIMEOUT_SECONDS`) |
| `npm install` | до 900 с |
| `playwright install chromium` | до 600 с |
| прогон e2e | до 900 с |

Итого худший случай ≈ **78 минут против 15**. Хуже того, фаза 4 идёт **после**
`deadline` и им вообще не ограничена: `RUN_TIMEOUT_SECONDS` покрывает только
циклы исполнения. Практический вывод: с дефолтным `timeout_seconds` браузерный
самотест не досчитает никогда — job умрёт раньше.

**Что сделать.**
- Ввести единый бюджет рана и выводить `timeout_seconds` задачи из него, а не
  наоборот; для задач с `github` в `allowed_tools` поднимать дефолт.
- Занести фазу 4 под общий `deadline` и передавать в неё остаток времени, а не
  фиксированные константы.
- Логировать фактическую длительность каждой фазы — сейчас нет ни одной цифры,
  по которой бюджеты можно откалибровать.

**Готово, когда:** ран с включённым `AUTOPILOT_E2E_ENABLED` доходит до PR, не убитый воркером, и в логе видно время каждой фазы.

**Сделано.** Бюджеты выводятся из одного места:
`RUN_TIMEOUT_SECONDS = EXECUTION_BUDGET_SECONDS (1200) + VERIFICATION_BUDGET_SECONDS (1500)`,
а `total_run_budget_seconds()` = клон + это + запас = **56 минут**. `enqueue_job`
берёт таймаут оттуда, но **только** для execute-job'ов, которые реально идут в
coding executor (роль есть в `OPENCLAW_AGENT_MAP` с `github` в `allowed_tools`) —
зависший OpenClaw-job по-прежнему объявляется мёртвым через 15 минут. Внутри
рана два дедлайна: циклы исполнения не могут съесть долю верификации, а
`run_browser_self_test(budget_seconds=...)` режет таймаут каждого шага по остатку
и честно отдаёт `skipped`, если времени не хватает, вместо того чтобы быть
убитым на середине. Длительность каждой фазы пишется в `timings` и в лог.

### [x] 2. Не терять работу при падении push / PR

**Проблема.** `_push_branch` и `_open_pull_request`
([coding_executor.py:823-824](../../backend/services/coding_executor.py#L823))
кидают `RuntimeError` / `HTTPStatusError`. В
[orbit_commander.py:1640](../../backend/services/orbit_commander.py#L1640)
ловится **только** `CodingExecutorUnavailable`, значит исключение уходит наверх,
воркер помечает job на ретрай — и весь ран повторяется с нуля: новый клон, новый
прогон модели. Коммит, который уже был сделан, лежал в `TemporaryDirectory` и
удалён вместе с ней.

Вторая грань: `_branch_name` детерминирован (`autopilot/<task-id>-<slug>`). Если
push прошёл, а создание PR упало, то на ретрае push в ту же ветку получит
non-fast-forward, а `POST /pulls` — 422.

**Что сделать.**
- Обернуть push/PR так, чтобы сетевой сбой возвращал `CodingExecutionResult(success=False)`
  с понятной причиной, а не пробивал наверх.
- Сделать шаг PR идемпотентным: перед созданием проверять существующий PR для
  ветки (`GET /pulls?head=…`) и возвращать его URL.
- Разнести ретраи: суффикс попытки в имени ветки либо переиспользование ветки с
  `--force-with-lease` (осознанно, только для `autopilot/*`).

**Готово, когда:** тест с замоканным 502 от GitHub даёт `success=False` с
внятной ошибкой, а повторный ран по той же задаче не падает на конфликте ветки.

**Сделано.** `push`/`_open_pull_request` обёрнуты: сетевой сбой возвращает
`CodingExecutionResult(success=False)` с сохранёнными планом, findings и
верификацией, а не пробивает наверх в generic-ретрай воркера. PR идемпотентен —
перед созданием ищется уже открытый для ветки, и 422 тоже разрешается поиском.
`_branch_name` получил суффикс попытки (`-a2`, `-a3`), поэтому ретрай после
частично прошедшего push не упирается в non-fast-forward. В ленте задачи
появилось событие `coding_executor_delivery_failed` — «работа была готова, не
доставили» больше не выглядит как «модель не справилась».

**Осталось (учтено в пункте 4):** сам коммит по-прежнему живёт в
`TemporaryDirectory`, поэтому ретрай повторяет прогон модели. Полное устранение
требует постоянной рабочей копии.

## P1. Работает, но вслепую или дорого

### [!] 3. Завести выделенный тестовый аккаунт и сид-данные

Фаза 4 **ни разу не отрабатывала целиком**: позитивный логин не проверен, потому
что тестового пользователя не существует. Проверен только негативный путь
(форма заполняется, Supabase отвечает `Invalid login credentials`, тест падает
там, где должен).

- Завести отдельного пользователя Supabase только для e2e, не рабочий аккаунт.
- Сид минимального набора данных (организация, пара клиентов, задача), иначе
  маршруты отрендерятся пустыми и проверка выродится в «страница не упала».
- Заполнить `.env.e2e.local` и один раз прогнать спеку целиком зелёной.

**Готово, когда:** `npx playwright test e2e/autopilot-smoke.spec.ts` зелёный
локально, и `run_browser_self_test` возвращает `passed`, а не `skipped`.

**Заблокировано: нужно действие владельца проекта.** Заводить аккаунты и
вводить пароли агент не может — это делается руками. Со стороны кода готово всё
остальное: гейт, передача учётных данных через окружение, скрабинг вывода,
корректный `skipped` без настроек. Требуется:

1. создать в Supabase отдельного пользователя только для e2e;
2. `cp .env.e2e.example .env.e2e.local` и заполнить `AUTOPILOT_E2E_EMAIL`,
   `AUTOPILOT_E2E_PASSWORD`, `AUTOPILOT_E2E_SUPABASE_ANON_KEY`,
   `AUTOPILOT_E2E_ENABLED=true`;
3. один раз прогнать спеку и убедиться, что она зелёная.

### [x] 4. Убрать холодную установку зависимостей из каждого рана

Сейчас каждый ран делает `git clone --depth 1` (~465 МБ), затем `npm install`,
затем `playwright install chromium`. Это основная часть тех самых 78 минут.

- Прогретый кэш: `npm_config_cache` и `PLAYWRIGHT_BROWSERS_PATH` на постоянном
  томе (частично уже пробрасываются в `e2e_environment`).
- Либо образ с уже установленными зависимостями и браузером, в который
  монтируется только рабочая копия.
- Рассмотреть `git worktree` от локального зеркала вместо полного клона —
  каталог `.selfdev/` под это уже зарезервирован в `.gitignore`.

**Готово, когда:** повторный ран тратит на подготовку окружения меньше минуты.

**Сделано.** Появился `AUTOPILOT_CACHE_DIR` (по умолчанию `.selfdev/cache`, уже
git-ignored): `npm_config_cache` и `PLAYWRIGHT_BROWSERS_PATH` указывают туда и
переживают удаление рабочей копии, поэтому браузер и дерево зависимостей
скачиваются один раз, а не каждый ран. Явно экспортированное значение с хоста
по-прежнему выигрывает. Установка перешла на `npm ci` при наличии
`package-lock.json` (детерминированнее и быстрее) с откатом на `npm install`,
если лок разошёлся с `package.json`. Недоступный каталог кэша деградирует в
холодный ран, а не в упавший.

**Осталось:** сам клон по-прежнему полный (`--depth 1`, ~465 МБ). Переход на
`git worktree` от локального зеркала — отдельный шаг, он же закроет остаток
пункта 2 (постоянная рабочая копия вместо `TemporaryDirectory`).

### [x] 5. Снять baseline «чужого» шума, иначе проверки бессмысленны

В репозитории уже есть **141 ошибка** `npx tsc --noEmit` и **3 падающих теста**
в `test_openclaw_security.py` (проверено прогоном на чистом дереве — они не от
этой ветки). Модель не может отличить сломанное ею от сломанного до неё, поэтому
любое «прогони тесты перед finish» будет давать ложные срабатывания.

- Снять и закоммитить baseline (счётчик ошибок или список), сравнивать дельту, а
  не абсолют.
- Добавить в `ALLOWED_COMMAND_PREFIXES`
  ([coding_executor.py](../../backend/services/coding_executor.py)) e2e-команды,
  чтобы исполнитель мог проверять себя **до** `finish`, а не только пост-фактум.
- Отдельной задачей (не в ветке автопилота) разобрать сам долг.

**Готово, когда:** исполнитель может запустить проверку и получить ответ «ты
добавил N новых ошибок», а не «в проекте 141 ошибка».

**Сделано, но иначе, чем планировалось.** Вместо коммита baseline-счётчика
(который пришлось бы поддерживать и который врёт при любом чужом коммите)
сделана атрибуция по файлам: инструмент `check_changes` берёт список
изменённых в этом ране файлов из `git diff --name-only` и фильтрует
диагностику по ним. Ответ модели выглядит так:

```
Проверка «typescript»: 1 замечани(й) в изменённых тобой файлах
(всего в проекте — 142, остальное существовало до тебя).
src/lib/autopilot-check-probe.ts(3,10): error TS18048: 'value' is possibly 'undefined'.
```

Проверено на живом репозитории с намеренно сломанным файлом: из 142 ошибок
атрибутирована ровно одна, и именно нужная. Поддержаны `typescript`, `lint`,
`tests`; в `ALLOWED_COMMAND_PREFIXES` добавлены `npx eslint`,
`npx playwright test`, `npm run test:e2e`; system prompt требует прогнать
`check_changes` перед `finish`.

**Осталось:** `typescript` и `lint` требуют `node_modules`, которых в свежем
клоне нет до фазы верификации — сейчас инструмент честно об этом сообщает
вместо «command not found». Закроется вместе с постоянной рабочей копией из
пункта 4.

## P2. Качество самой проверки

### [x] 6. Генерировать сценарий под конкретную задачу

Сейчас всегда прогоняется одна и та же смоук-спека. Исходное требование —
проходить **user flow, созданный в рамках задачи**. Точка расширения уже есть:
`run_browser_self_test(workdir, spec=...)`.

- Планировщик отмечает, какой пользовательский путь затрагивает задача.
- Верификатор генерирует временную спеку под этот путь (не коммитить её) либо
  выбирает подходящую из `e2e/`.
- Смоук остаётся всегда как нижняя граница.

**Сделано.** `select_spec` сопоставляет заголовок задачи, описание, критерии
приёмки и список изменённых файлов с именами спек в `e2e/` и выбирает
подходящую; смоук — пол, а не потолок. Выбранный сценарий записывается в
`verification.spec` и печатается в отчёте, чтобы отчёт не подразумевал больше
покрытия, чем было куплено. Генерацию новой спеки под задачу сознательно не
делал: выбор из существующих даёт основную пользу без риска, что автопилот
«проверит себя» тестом, который сам же и написал под свой результат.

### [x] 7. Ревизия больших диффов не должна молча обрываться

`MAX_DIFF_CHARS = 60_000` ([autopilot_verifier.py:143](../../backend/services/autopilot_verifier.py#L143)):
всё сверх этого просто отрезается, в отчёте пишется «(обрезан)», но какие файлы
не посмотрели — не сказано.

- Резать дифф по файлам и ревьюить пачками, сводя findings.
- В отчёте явно перечислять, что не попало в ревизию.

**Сделано.** `chunk_diff` режет дифф по файлам на части (до 4 запросов ревью,
каждый до 60k, отдельный файл до 20k), findings из частей дедуплицируются.
Файлы, не поместившиеся в бюджет, попадают в отчёт отдельным замечанием со
списком имён — «не проверено ревизией» больше не выглядит как «проверено и
чисто». Сбой провайдера на одной части не теряет остальные.

### [x] 8. Решить, что делать с непочинёнными блокерами

Сейчас круг починки один, и после него `success=True` даже если `blocker` остался
— он лишь попадает в тело PR и в событие `autopilot_review_findings`.

- Либо второй круг починки, либо явная пометка PR как draft при оставшемся
  блокере, либо передача в QA-фазу как жёсткого гейта. Сейчас поведение
  «сообщили и поехали дальше» — это осознанный, но не задокументированный выбор.

**Сделано.** `AUTOPILOT_BLOCKER_POLICY` (по умолчанию `draft`): при оставшемся
блокере или упавшем браузерном тесте PR открывается черновиком и с пометкой
`[требует внимания]` в заголовке — смёржить случайно уже нельзя. Значение
`warn` возвращает прежнее поведение.

### [x] 9. Показать план и верификацию в интерфейсе

`plan`, `review_findings`, `verification` уже лежат в `ai_tasks.result`, но
[self-development.tsx](../../src/routes/self-development.tsx) их не рисует.
Прогресс по шагам и статус самотеста — ровно то, ради чего это писалось.

**Сделано.** Компонент `AutopilotRunPanel` в карточке задачи показывает статус
каждого шага плана, результат браузерного самотеста с именем сценария, findings
самопроверки и ссылку на PR. Разбор `ai_tasks.result` вынесен в
`autopilot-result.ts` и покрыт тестами на битые данные: колонка — нетипизированный
JSON, а строки, созданные до автопилота, этих полей не содержат вовсе, и
исключение при разборе уронило бы весь диалог задачи.

## P3

### [x] 10. Скрабинг по форме, а не только по списку известных значений

`_secret_values()` собирает секреты из настроек. Токен, которого нет в
`settings` (например, JWT из сетевого лога Playwright), не будет вычищен.

- Добавить маскирование по образцу: `eyJ…` (JWT), `github_pat_…`, `sk-…`.

**Сделано.** `scrub` делает два прохода: по известным значениям из настроек (это
ловит секрет без узнаваемой формы) и по образцам — JWT, `ghp_`/`github_pat_`,
`sk-`, `nvapi-`, `xox*`. Проверено, что обычный текст не портится.

### [x] 11. Метрики жизненного цикла

Доля ранов, дошедших до PR; сколько шагов в среднем блокируется; сколько findings
чинится с первого круга; доля `passed` / `failed` / `skipped` в фазе 4. Без этого
непонятно, автопилот улучшается или деградирует.

**Сделано.** Модуль `autopilot_metrics`: `run_metrics` разворачивает результат
рана в строку метрик (доставлен ли PR, тип рабочей копии, доля выполненных
шагов, число блокирующих findings, статус верификации, время по фазам),
`aggregate` сводит набор ранов. Две тонкости зафиксированы тестами: ран без
плана даёт `None`, а не нулевую полноту (иначе «плана не было» усреднится с
«ничего не сделано»), а `skipped`-верификация не идёт в знаменатель pass rate,
иначе ненастроенное окружение выглядело бы зелёным. Строка метрик публикуется
событием `autopilot_metrics` в ленте задачи.

## Порядок

Все пункты, кроме 3, выполнены. Пункт 3 упирается в действие владельца проекта:
создать тестовый аккаунт Supabase и заполнить `.env.e2e.local`. Со стороны кода
для него готово всё.

Постоянная рабочая копия сделана в рамках пункта 4 и закрыла три хвоста разом:
полный клон в каждом ране, потерю коммита при сбое доставки (появился
`_resume_delivery`) и коллизии имён веток при ретрае.

Что осталось за рамками этого плана и потребует отдельного решения:

- `typescript` и `lint` в `check_changes` по-прежнему требуют `node_modules`.
  Постоянная копия их сохраняет, поэтому после первого прогона верификации
  проверки станут доступны и во время исполнения — но на самом первом ране в
  свежем слоте их всё ещё нет.
- Генерация спеки под задачу (а не выбор из существующих) — сознательно не
  сделана: есть риск, что автопилот проверит себя тестом, написанным под
  собственный результат.
- Метрики пишутся событием в ленту задачи; отдельного хранилища и дашборда нет.
